# Workload Identity & ServiceAccount Security

This document details the security rationale and implementation guidelines for managing workload identities inside the SecureHaven Kubernetes lab.

---

## 1. Rationale for Dedicated ServiceAccounts

By default, any pod created in Kubernetes that does not specify a `serviceAccountName` is automatically assigned the `default` ServiceAccount of its namespace.
If multiple workloads share the same default identity:
- **Blast Radius**: A security compromise in one workload (e.g. `research-app`) inherits the exact same service account credentials as other workloads in that namespace.
- **Audit Logging**: Logs generated by the API server will show all actions coming from the generic `system:serviceaccount:<namespace>:default`, preventing attribution.

**Remediation**:
Each application and database is given a dedicated identity (e.g., `research-app-sa`). This restricts identity scope and enables distinct audit records.

---

## 2. Preventing Token Automounting

In standard configurations, Kubernetes injects a JWT API token into the container's file tree. 
An attacker who compromises a container and gains shell access can read this token to communicate directly with the Kubernetes API server.

### 2.1 Defense in Depth Controls
We enforce token restriction at two distinct layers:
1. **ServiceAccount Spec**:
   ```yaml
   automountServiceAccountToken: false
   ```
2. **Pod Template Spec**:
   ```yaml
   automountServiceAccountToken: false
   ```
This ensures that even if a developer accidentally overrides the ServiceAccount configuration or deploys a pod manually, token mounting remains disabled.

## 3. Compromised Pod Threat Analysis

If an attacker compromises `research-app` and attempts lateral movement:

```
Compromised Pod [research-app]
  └── Attacker Shell Access
        ├── Attempt: Read SA Token File (/var/run/secrets/...)
        │     └── Result: Directory Empty (Token Not Mounted)
        │
        ├── Attempt: Anonymous API queries (https://kubernetes.default.svc)
        │     └── Result: HTTP 403 Forbidden (RBAC Default Deny)
        │
        └── Attempt: Access other namespaces' secrets/resources
              └── Result: Access Denied (Strict Namespace Isolation)
```

## 4. Comparison: Local Secrets vs. Production IAM / KMS

| Security Area | Local Kubernetes Lab | Production Cloud Environment |
|---|---|---|
| **Secret Storage** | Kubernetes `Secret` resources (Base64-encoded) | KMS-encrypted database secrets (AWS KMS, Azure Key Vault, HashiCorp Vault) |
| **Secret Injection** | Statically mounted env vars via `secretKeyRef` | Secrets CSI Driver mounting secrets as memory-backed filesystems or dynamically fetched via SDK |
| **Workload Identity** | Local Kubernetes ServiceAccount | IAM Role Workload Identity (AWS IRSA, Azure AD Workload Identity, GCP Workload Identity Federation) |
| **Authentication** | Token automounting disabled | Ephemeral IAM OIDC federation tokens minted on demand |

---

## 5. Verification Matrix

- **Statically Verified**: The presence of `automountServiceAccountToken: false` and custom `serviceAccountName` values in all deployment and ServiceAccount YAML files is checked by `rbac_tests.js`.
- **Runtime verification**: Confirming that the `/var/run/secrets/kubernetes.io/serviceaccount/` directory is empty inside a live running container.
